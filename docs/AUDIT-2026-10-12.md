# Holodeck audit — 12 Oct 2026

**Question asked:** Holodeck is meant to be a standalone project that can render and animate anything from real-time data, with full drag-and-drop editing and pluggable component libraries and themes (including third-party ones), compatible with the Hyperdrive extension system. How close are we?

**Short answer:** about a third of the way, and lopsided. The 2.5D process editor is a real, well-tested editor with a working library/theme/animator model and a live-data path. Everything around it is scaffold-grade: no data provider has ever been implemented, the 2D editor cannot persist an edit, the 3D viewer has no library wiring, nothing is published to npm, there is no CI for the monorepo, and the CLI does not build. Third-party libraries work in-process by static import only; there is no manifest, loader, version check or trust model.

Scope: `holodeck/`, `holodeck-sdk/`, `holodeck-importer-brainboard/`, and the Hyperdrive consumers in `core/`. Evidence gathered on branches `holodeck@feat/iso-auto-routing`, `core@feat/brewery-extensions`, `holodeck-sdk@feat/contribution-registry`. A concurrent session is refactoring `core` (flat-2d → `hyperdrive-ui-control`, flow registry moved to `hyperdrive-ui/app/components/logic/flow/registry.ts`); paths below reflect the tree as read.

## 2. Rendering surfaces

### 2.5D process editor (`@holodeck/editor-2.5d-react`, ~12.8k LOC)
The only surface that meets the bar. R3F on WebGPU with an orthographic iso camera, instanced pools for pipes/elbows/valves, GLB parts through a style layer (`applyHolodeckStyle`) that enforces the Arcentry look, and a parts registry. Three fidelity rounds against `tests/snapshots/reference.jpg` got pipes, bends, valves and tanks close to the reference; remaining gaps are tank wall facet density and handwheel spokes at zoom.
Weak spots: WebGPU-only (Chrome ≥ 113, no fallback); scene format is its own `IsoSceneFile` (grid placements), not the SDK `SceneFile`; module-level style constants in `Shell.tsx` and tank params are frozen at import, so themes don't reach everything.

### 2D editor (`@holodeck/editor-2d-react`, React Flow)
Renders a `SceneFile` as React Flow nodes with dagre auto-layout, palette shell, and registry-driven node/edge types. It is not an editor yet: nodes/edges are re-derived from the `scene` prop every render and there are no `onNodesChange` / `onEdgesChange` / `onConnect` handlers, so drags, connections and deletes never reach the host (`HolodeckEditor2D.tsx:100-141`). `reactFlowToSceneFile` exists but nothing calls it. Label edit is `window.prompt`. Auto-layout overrides manual positions unless `layout='manual'`.

### 3D viewer (`@holodeck/viewer-3d-react`)
Read-only by design (`README.md:3`). OrbitControls, click-select one node, ISA-101 status colouring, keyframe animation runner. Takes `objectRenderers` as a prop; **no registry wiring** — the `holodeck.scene3d.renderer` kind named in `EXTENSIONS_AND_LIBRARIES.md` §2 is a string constant nobody registers or consumes. Needs WebGPU; shows `WebGPUMissing` otherwise. 11 unit tests, none render the component.

## 3. Real-time data

- `Provider` (`holodeck-sdk/ts/src/index.ts:331-353`) has **no implementation** anywhere except a README snippet and a mock in `holodeck/examples/basic-usage/example.ts` (which itself doesn't type-check: uses `nodeIDs`, SDK says `nodeIds`). `provider-template/` and `importer-template/` are empty directories. ROADMAP Phase 5 "Not started".
- No viewer or editor calls `provider.query` / `subscribe`. `HolodeckProvider.tsx` in 2D is a stub; `useHolodeck` throws.
- How data arrives today, per surface:
  - 2.5D: `metrics?: Record<placementId, Record<param, value>>` prop → `resolveParams(def, placement, metrics)` → part props and animators. Works, host-pushed.
  - 3D: a re-rendered `scene` whose `node.status`/`node.metrics` changed; built-in meshes read only `status`; `metrics` is visible only through host `objectRenderers` (Hyperdrive's factory-3d pack does this).
  - 2D: `status` tints nodes; `metrics` is copied into node data and never read.
- There is **no SDK binding model** ("node property X ← metric Y, with transform"). Bindings exist only in Hyperdrive's `hyperdrive.bindings` extension bag, implemented twice (`core/.../hmi/scene-bindings/apply-scene-bindings.ts` for 3D, `hyperdrive-extensions/src/iso-bindings.ts` for 2.5D) with a duplicated `lookupLiveValue`. `SceneComponentPack.overlayAdapter` is never called by any Holodeck package.
- Every WebSocket tick rebuilds the whole `SceneFile`/metrics object; no per-node subscription or dirty tracking.

**Verdict:** "real-time data" is a host responsibility today. A third party cannot point Holodeck at Prometheus/OPC UA/MQTT and see anything move.

## 4. Animation — three models that don't meet

| Model | Where | Driven by | Consumed by | State |
|---|---|---|---|---|
| SDK keyframes (`Animation`/`AnimationTrack`/`Keyframe`, `SceneNode.animations`) | `holodeck-sdk` | time | 3D `AnimationRunner` only; transform + `visible` paths only; edges ignored | partial |

| 2.5D `IsoAnimator` (`holodeck.iso.animator`, `def.animNodes`, `placement.animation`) | `editor-2.5d-react/src/anim` | **data** (param value) | 2.5D GLB `anim.*` nodes; spin/fill/bob/visible/pulse + brewery `fill-pct`/`pump-spin`/`steam`; tested | works |

The only chain that animates from live data is 2.5D-specific and has no SDK type. The SDK has no notion of "animator driven by a metric".

## 5. Editing, per surface

**2.5D** — controlled `ProcessEditor` (`scene`, `onChange`, `mode: run|edit`, `metrics`, `registry`, `selectedId`, `inspector`):
works: move (one undo step per drag), rotate 90° (inspector only, no hotkey), resize handles for parts declaring `def.resize`, delete, undo/redo (50 snapshots, ⌘Z/⇧⌘Z), half-cell snap + floor grid, click-click pipe drawing with A\* obstacle routing + port snapping + live ghost + `R` reroute, inspector from `IsoPartParamSpec` + host panels, run-mode lock, shortcuts (Space pan, Esc, Del, V, P, R, Q/E view, X top-down).
missing: true drag-*drop* from palette (palette `onDragStart` just enters place mode), multi-select/marquee, copy/paste/duplicate, alignment guides, z-order/groups/layers, per-object lock, drag-a-pipe-end-to-another-port, pinch zoom, keyboard navigation of parts (WebGL canvas), theme picker UI. Shortcut keys V/P/R/Q/E/X fire even with ⌘/Ctrl held.

**2D** — palette drag → `onDropPaletteItem` callback only; everything else (move/connect/delete/undo/inspector) is missing as persisted edits. Multi-select/marquee are React Flow defaults.

**3D** — read-only; single click-select; `selectedNodeIds` highlight.

**Format split:** SDK `SceneFile` is the interchange for 2D and 3D; 2.5D uses `IsoSceneFile` (deprecated aliases `SceneFile`/`ScenePlacement` point at the iso types, which will confuse consumers). Converting is listed as a follow-up in `EXTENSIONS_AND_LIBRARIES.md` §7.

## 6. Component libraries (incl. third-party)

**What works:** `ContributionRegistry` (`holodeck-sdk/ts/src/registry.ts`): kinds registered per editor, atomic install, duplicate-id rejection naming the other owner, `pending()` for kinds no editor has registered yet with replay on late registration, uninstall with hooks, `subscribe`, conformance kit. 2D registers `holodeck.flow.{nodeType,edgeType,palette}`; 2.5D registers `holodeck.iso.{part,theme,animator,inspector}`. A library can contribute, per surface:

| | 2D | 2.5D | 3D |
|---|---|---|---|
| parts / node components | ● | ● (component, footprint, ports, params, defaults, GLB, animNodes, instanced renderer, resize) | prop only |
| palette entries | ● | ● (derived from parts) | — |
| themes | ○ | ● | ○ |
| animators | ○ | ● | ○ |
| inspector panels | ○ | ● | ○ |

**What's missing for "built by others":**
1. **Loading.** Everything is a static `import`. `ExtensionHost.install(ext)` takes an in-memory object; nothing fetches, resolves or verifies a package. No dynamic `import()` path, no URL/npm loader.
2. **Manifest & discovery.** `HolodeckExtension.version` is an unvalidated string; no `sdkRange`/API version, no inter-extension dependencies, no declared peer requirements (React/three versions). Namespacing (`brewery:fermenter`, `hyperdrive.brewery`) is convention only. CLI discovery (`@holodeck/importer-*`) is referenced by `generate.ts` but `utils/discovery.ts` does not exist.
3. **Trust.** Parts, animators and inspectors are arbitrary React/JS run in-process with page privileges. No signature, integrity hash, permission model or certification enforcement.
4. **Lifecycle edges.** Uninstalling a library whose parts are in an open scene is not handled; `parseSceneFile` throws on unknown part ids instead of degrading to a placeholder.
5. **Legacy path.** `packToExtension` drops `layoutConfig` and `overlayAdapter`; Hyperdrive's `factory-3d/pack.ts` still builds a raw `SceneComponentPack`.
6. **3D** has no kinds at all.

## 8. Hyperdrive compatibility

- `HyperdriveExtension` is `HolodeckExtension` plus typed optional Hyperdrive kinds (`hyperdrive.iec.library`, `hyperdrive.fbd.block`, `hyperdrive.hmi.bindings`). `BREWERY_EXTENSION` installs through `ExtensionHost` → `toHolodeckExtension` → `registry.install`, reaching the 2.5D editor and the FBD palette. A pure third-party `HolodeckExtension` with only `holodeck.*` kinds installs the same way; Hyperdrive kinds stay `pending` where no editor registered them. Holodeck never imports Hyperdrive. **This direction is sound.**
- **Manifest gap.** `hyperdrive.package.v1` (`core/docs/schemas/hyperdrive-package.manifest.v1.schema.json`, `additionalProperties:false`) describes IEC `sources`/`exports` and a `ui: {npm, registrations: logicFlow|control|viewer3d}` sidecar aimed at the legacy `SceneComponentPack`; nothing reads `manifest.ui`; there is no `iso`, no pack entry point, no SDK range, no mapping from module path to extension id; `exports.graphics` is an untyped path list; `certification.claims` has no registry-side counterpart. The brewery library is a private workspace package with no `hyperdrive.package.json` and ships its `.plc` as `?raw` JS strings rather than as package `sources`.
- Doc/code drift: doc names `createDefaultExtensionHost()` (code: `createExtensionHost` / lazy `getDefaultExtensionHost`); doc says 3D registers `holodeck.scene3d.renderer` (it doesn't); doc references `hyperdrive-ui-flat-2d/src/registry.ts` (moved by the concurrent refactor).

## 9. Standalone packaging

- **Not on npm:** `@holodeck/sdk`, `@holodeck/viewer-3d-react` → E404. All packages depend on the SDK via `file:../../../holodeck-sdk/ts`; a published tarball would be unresolvable.

## 12. Proposal: third-party libraries & themes, Hyperdrive-compatible

Keep the registry as the in-memory truth; add the three missing layers around it. Nothing here changes `ContributionRegistry` semantics.

**A. One manifest for a UI pack — `holodeck.extension.v1`** (JSON, lives in the npm package root and is what a store lists):
```json
{
  "schemaVersion": "holodeck.extension.v1",
  "id": "acme.dairy",
  "version": "1.2.0",
  "sdk": ">=0.1 <0.3",
  "peers": { "react": ">=19.2", "three": "^0.186" },
  "entry": "./dist/extension.js",
  "kinds": ["holodeck.iso.part", "holodeck.iso.theme", "holodeck.theme", "holodeck.flow.palette"],
  "requires": ["hyperdrive.stdlib-ui@^0.1"],
  "assets": "./assets/",
  "integrity": "sha256-…",
  "certification": { "claims": [] }
}
```
`entry` default-exports a `HolodeckExtension`. `kinds` is declared up front so a host can refuse packs it cannot host and show `pending` honestly. `assets` fixes the GLB problem: parts reference models by `asset:` id, the loader resolves to URLs (replaces `import.meta.glob`).

**B. Loader in the SDK** — `loadExtension(source: URL | npmSpecifier | File, { host, verify })`: fetch manifest → check `sdk`/`peers`/`kinds` → verify `integrity` (and later signature) → dynamic `import(entry)` → `registry.install`. Same loader runs in the CLI (`holodeck validate <pack>`) and in the Hyperdrive store client. Static imports stay for built-ins.

**C. Cross-surface theme kind — `holodeck.theme`**: a palette token set (surface, line, body, accent, status.normal/warning/critical/bad-quality, selection) + per-surface sections (`iso: HolodeckStyle`, `flow: CSS custom properties`, `scene3d: status map`). 2D CSS becomes `var(--hd-*)`; 3D `colorForStatus` reads the theme; 2.5D maps tokens onto `HolodeckStyle`. Ship `holodeck.isa101` (grey-normal) and `holodeck.arcentry` as built-ins; a theme pack is just an extension with this kind.

**D. Hyperdrive bridge** — in `hyperdrive.package.v1`: replace `ui.registrations` enum with `ui.holodeck: { manifest: "./ui/holodeck.extension.json" }`, add `compatibleRuntime.holodeckSdk`, map `module@version` → extension id (`hyperdrive.<module-path>`), and have `exports.graphics` entries typed (`iso-scene`, `scene-file`). One store listing = one `hyperdrive.package.v1` whose `ui.holodeck` points at an A-manifest; `ExtensionHost.installPackage(pkg)` installs IEC sources and the UI pack together and uninstalls them together. Carry `certification.claims` into the registry (`ownerOf` → listing) so deploy policy can gate `SF_*` and in-process UI code alike.

**E. Safety rails** — unknown part id in a scene renders a labelled placeholder instead of throwing; uninstall refuses (or warns) when an open scene references the pack; a per-extension error boundary around contributed React components so one bad pack cannot blank the editor.
